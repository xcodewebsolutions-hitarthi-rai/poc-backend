# 生成准确性保障（Evidence Gate）

> **加载时机**：生成任何包含 YonSQL / 业务对象 URI / 字段的代码前。
> **职责**：在无法运行元数据查询、无法连接数据库时，通过"证据表 + 代码标注 + 人工校验清单"三层机制，最大限度防止臆想。
> **核心原则**：生成代码必须自带"待验标记"，让人工校验时一眼看到哪些可信、哪些必须查。

---

## 1. 为什么需要这一层

元数据查询脚本可能因环境/鉴权问题无法运行，数据库也可能连不上。

此时不能依赖"先查后写"，但也不能放任臆想。

本门禁的核心思路：

- **不阻止生成**，但**强制标注可信度**。
- **不替代人工校验**，但**让校验有的放矢**。
- **不假装能自动验证**，而是**诚实暴露不确定性**。

---

## 2. 第一层：Evidence Gate（证据表）

### 2.1 强制规则

生成任何包含 YonSQL / URI / 字段的代码前，**必须**先输出证据表。

**没有证据表，不许输出代码。**

### 2.2 证据表格式

```markdown
## 证据表

| URI | domain | 字段 | 可信度 | 来源 |
|---|---|---|---|---|
| voucher.order.OrderDetail | udinghuo | id, orderId | 🟢 已确认 | 用户明确给出 |
| FIAR.FIAR.ARSureEventBody | yonbip-fi-earap | sourceChildId, freeChId(refUri), amountField | 🟡 待确认 | 方案文档记录，需人工到平台核实 |
| 当前事实锁 | — | 当前业务对象/子表/字段组 | 🟢 已确认 | 最新提示词 + 当前元数据 |
| 废弃对象排除 | — | 旧 URI/旧子表/旧特征组 | 🔴 禁止使用 | 自动事实漂移检测 |
```

### 2.3 可信度定义

| 标记 | 含义 | 条件 |
|---|---|---|
| 🟢 已确认 | 可以直接用 | 用户在需求中明确给出，或本轮实际调了元数据查询 |
| 🟡 待确认 | 可以生成，但必须标注，人工必须校验 | 来自文档/经验/推断，未经平台元数据验证 |
| 🔴 禁止使用 | 不许出现在代码里 | 无任何来源依据，纯臆想 |
| 🔴 禁止使用 | 不许出现在代码里 | 自动事实漂移检测判定为废弃对象或旧事实 |

### 2.4 来源类型

"来源"列只允许以下值：

- `用户明确给出` — 用户在需求/对话中说了
- `方案文档` — 仓库内有对应方案文档记录
- `元数据查询结果` — 本轮实际调了元数据脚本（环境可用时）
- `推断（需校验）` — 来自经验/模式匹配，必须标注 🟡
- `自动事实漂移检测` — 用于标记废弃对象和排除关键词

**禁止**留空或写"常见"/"通常"/"一般"。

## 3. 第二层：代码内强制标注

对于所有 🟡 待确认的 URI / 字段，**必须在代码注释中显式标注**，让人工打开代码就能看到。

### 3.1 标注格式

```javascript
// ⚠️ 待确认 URI：FIAR.FIAR.ARSureEventBody
//    来源：方案文档，未经平台元数据验证
//    待确认字段：sourceChildId / freeChId(refUri) / amountField
//    待确认类型：freeChId 是否为参照；amountField 是否为目标实体字段
var sql = 'select sourceChildId, freeChId, (select amountField from freeChId) as amountInfo ' +
  'from FIAR.FIAR.ARSureEventBody ' +
  'where sourceChildId in (' + this.wrapInQuotes(lineIds) + ')';
```

### 3.2 标注规则

- 每个 🟡 URI 上方必须有 `⚠️ 待确认` 注释块。
- 注释块必须写明：URI、来源、待确认字段。
- 🟢 已确认的 URI 不需要标注，但建议在证据表中已说明。
- 如果整段查询都是 🟡，注释块放在查询语句上方。
- 如果只有部分字段 🟡，在字段行末标注。

### 3.3 禁止

- 禁止把 🟡 当 🟢 用（不标注直接写）。
- 禁止把 🔴 写进代码（无来源依据的字段不许出现）。

## 4. 第三层：人工校验清单

拿到生成的代码后，人工按以下顺序逐项校验。

### 4.1 校验证据表

| 步骤 | 动作 | 通过标准 |
|---|---|---|
| 1 | 检查证据表是否输出 | 必须有证据表，没有则退回 |
| 2 | 标记所有 🟡 项 | 这些是校验重点 |
| 3 | 确认没有 🔴 项 | 代码里不应出现纯臆想的内容 |

### 4.2 上平台核实 URI 和 domain

| 步骤 | 动作 | 通过标准 |
|---|---|---|
| 4 | 对每个 🟡 URI，在平台元数据中搜索 | URI 必须能找到对应实体 |
| 5 | 确认 domain | `queryByYonQL` 第二个参数必须和平台元数据 `_entityInfo.domain` 一致 |
| 6 | 确认 tableName（参考） | 用于理解数据来源，不用于 YonSQL 拼装 |

### 4.3 逐字段比对

| 步骤 | 动作 | 通过标准 |
|---|---|---|
| 7 | 对每个 🟡 字段，在平台元数据 attributes 中查找 | 字段名必须存在于 `attributes[].name` |
| 8 | 确认字段类型 | 基本类型/参照/特征/子表/平行表/多选引用必须明确 |
| 9 | 确认嵌套或分步路径 | 参照确认 `refUri`，特征确认特征组和编码，平行表确认关联键 |

### 4.4 确认查询链路

| 步骤 | 动作 | 通过标准 |
|---|---|---|
| 10 | 从业务语义确认查询链路 | 例如：销售订单子表 → 确认应收 → 核销金额，这条链是否符合业务逻辑 |
| 11 | 确认关联字段 | 例如：用 `sourceChildId` 还是 `oriBillRowId` 关联，必须在元数据中确认 |
| 12 | 确认查询方向 | 正查还是反查，是否漏了中间表 |

### 4.5 确认代码注释

| 步骤 | 动作 | 通过标准 |
|---|---|---|
| 13 | 检查所有 ⚠️ 注释 | 每个 🟡 项都有对应注释 |
| 14 | 校验通过后删除 ⚠️ 注释 | 人工确认后，把 🟡 升级为 🟢，删除待确认注释 |

## 5. 与其他门禁的关系

| 门禁 | 职责 | 与本门禁关系 |
|---|---|---|
| 03_元数据门禁 | 定义"查什么、怎么查" | 本门禁是"查不了时的兜底保障" |
| 06_YonSQL信息充分性门禁 | 判断四要素是否充分 | 本门禁为"不充分时如何保证可校验" |
| 07_协同能力信息充分性门禁 | OpenAPI/事件/MDF 充分性 | 同上 |
| 04_输出契约 | 定义输出结构 | 证据表是输出契约的强制组成部分 |
| 09_最新需求事实锁定门禁 | 自动检测最新事实与历史事实漂移 | 本门禁负责把当前事实锁和废弃对象纳入证据表 |

---

## 6. 关键原则总结

1. **诚实暴露**：不知道就标 🟡，不要假装知道。
2. **可追溯**：每个 URI/domain/字段都要能追溯到具体来源。
3. **可校验**：🟡 项必须在代码中有 ⚠️ 注释，人工打开代码就知道要查什么。
4. **不放过**：🔴 纯臆想项不许出现在代码里。
