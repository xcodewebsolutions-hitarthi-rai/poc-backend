# YonScript 元数据消费门禁（强约束）

> **加载时机**：生成任何 YonScript 代码前
> **职责**：把"元数据必须查什么、查到什么程度、不查会出什么问题"全部明确为强约束门禁
> **与 01_技术规范.md 的关系**：`01_技术规范.md` 定义代码规范；本 reference 定义"代码生成前必须执行的元数据消费清单"

---

## 一、为什么需要门禁

### 1.1 错误样本（真实生产事故）

```javascript
// ❌ 反面教材（本次开发的真实错误）
// 凭"URI 前缀是 bd"就推导 domain 为 "basedoc"
var orgIdSql = "select id from `bd.adminOrg.BaseOrgVO` where code = '666666' and dr = 0";
var orgIdList = ObjectStore.queryByYonQL(orgIdSql, 'basedoc');
// 执行结果：Service not found / 返回空数组
```

**正确做法**：

```javascript
// ✅ 先调 iuap-c-metadata-info 查实体的 _entityInfo.domain
// 实际结果：domain = "ucf-org-center"
var orgIdList = ObjectStore.queryByYonQL(orgIdSql, 'ucf-org-center');
```

### 1.2 错误的根本原因

| 错误类型 | 出现频率 | 严重程度 | 典型症状 |
|---|---|---|---|
| 凭 URI 前缀推导 domain | 极高 | 高 | Service not found / 返回空 |
| 跨实体套用相邻 domain | 高 | 高 | 跨租户数据泄漏 / 数据错误 |
| 凭 dbColumnName 拼 SQL | 中 | 中 | 字段名错误 / SQL 解析失败 |
| 子表 key 凭经验写 | 中 | 高 | 子表查询为空 |
| 特征组编码凭印象 | 低 | 中 | 特征字段不更新 |
| 未真正跑 SQL 验证 | 极高 | 中 | 部署后才报错 |

## 二、门禁清单（生成代码前必走）

### 2.1 7 步元数据消费门禁

```
门禁 1: YonSQL 信息充分性判定
        - 先判断 uri/domain/字段/条件是否都已明确且可追溯
        - 四要素任一不明确，必须调 iuap-c-metadata-info
        - 四要素齐备时可直接拼装，但必须保留来源说明

门禁 2: 字段名必查 attributes
        - 主表/子表所有使用字段都必须在元数据 attributes 中存在
        - 禁止用 dbColumnName（用 name 属性）

门禁 3: 子表 key 必查 tables
        - 子表 key 来自元数据 tables.<key>，禁止臆想
        - 子表 URI 来自 tables.<key>._tableInfo.uri

门禁 4: 特征组编码必查 characterGroups
        - 特征组字段来自 characterGroups.<g>.features[].characterCode
        - 完整路径: vendorCharacterDefine.<characterCode>
        - 跨实体的特征组不能套用

门禁 5: 参照档案必查 refUri
        - 参照字段的 refUri 用于二次查询参照档案
        - 二次查询前必须查 refUri 指向实体的 attributes（含 code/name）

门禁 6: SQL 必执行验证
        - 写完 SQL 必须实际跑一次（带 limit 1 或小数据量）
        - 返回非空 + 字段类型符合预期 才算通过

门禁 7: 错误处理必捕获
        - queryByYonQL 返回空时必须显式判断
        - openLinker 返回非 200 必须日志记录
        - 任何异常不能让审核扩展"静默失败"
```

### 2.2 扩展：跨场景元数据依赖（v1.4.2 新增 ⭐）

> 邮件模板/公式模板的元数据消费门禁，覆盖到非 SQL 场景。

```
扩展门禁 M1: 邮件公式参数 uri 必须查元数据
            - 来源：单据实体的 _entityInfo.uri
            - ❌ 禁止凭 businessObjectCode 推导
            - ❌ 禁止用 'domain.billNo' 拼装
            - 详见: ../30-scenes/02_消息触达.md §5.0 门禁 C4

扩展门禁 M2: 公式参数 domainKey 必须 === others.domain
            - 共享同一来源（URL 的 feDomainKey）
            - 运行时校验：if (domainKey !== domain) throw
            - 详见: ../30-scenes/02_消息触达.md §5.0 门禁 C1

扩展门禁 M3: 公式参数 businessId/realDocumentId 强制 String 类型
            - 平台已 String 化，但需用 String() 显式转换
            - 详见: ../30-scenes/02_消息触达.md §5.0 门禁 C2/C3
```

### 2.3 门禁违反的代价

| 违反门禁 | 部署前能发现吗 | 部署后症状 |
|---|---|---|
| 门禁 1 (domain 错) | ✅ SQL 验证可发现 | 整段业务逻辑失效 |
| 门禁 2 (字段名错) | ✅ SQL 验证可发现 | 字段查询为空 |
| 门禁 3 (子表 key 错) | ✅ SQL 验证可发现 | 子表数据丢失 |
| 门禁 4 (特征组编码错) | ❌ API 调用时才暴露 | 特征字段不更新（静默失败）|
| 门禁 5 (参照 refUri 错) | ✅ SQL 验证可发现 | 参照字段为空 |
| 门禁 6 (未跑 SQL) | ❌ 部署后才暴露 | 整段业务失效 |
| 门禁 7 (无错误处理) | ❌ 偶发问题 | 数据不一致 |
| **M1 (uri 臆想)** | ❌ 邮件发送后公式不计算（**静默**）| 公式引擎找不到实体 |
| **M2 (domainKey 不一致)** | ❌ 公式部分计算或全错 | 域解析错 |
| **M3 (businessId 类型错)** | ❌ 公式渲染失败 | String ↔ Long 类型不匹配 |

**结论**：门禁 1-5 必须在生成代码前完成；门禁 6-7 必须在生成代码后立即执行。

## 三、门禁执行流程（强制）

### 3.1 生成 SQL 前的元数据消费顺序

```
Step 1: 先判断 YonSQL 四要素是否充分
        - uri / domain / 字段 / 条件是否已经明确
        - 若充分且可追溯，可直接拼装，不强制补查
        ↓
Step 2: 若不充分，再按业务对象名称或用户提供的业务语义调用 iuap-c-metadata-info
        若用户已给出 URI，则按 URI 查询
        命令: python scripts/ultimate_metadata_query.py --query-uri "<uri>" --format structured
        ↓
Step 3: 提取元数据消费清单
        - _entityInfo.uri / domain / pk
        - tableName / schema 仅用于核对，不用于 YonSQL 拼装
        - attributes[].name（字段名）
        - attributes[].type / dataType / refUri（字段类型与参照）
        - tables.<key>（子表信息）
        - characterGroups.<g>（特征组信息）
        - referenceStructure（参照信息）
        - 平行表独立 URI/domain/关联键（如需求涉及）
        - 业务外键关联的源实体 domain、目标实体 domain、外键字段（如需求涉及）
        ↓
Step 4: 先按字段类型选择写法，再用消费清单拼装 YonSQL（每条查询都标注消费来源）
        ↓
Step 5: 实际执行 SQL 验证（带 limit 1 + dr = 0）
        ↓
Step 6: 通过验证后才进入代码生成阶段
```

补充强约束：

- 如果用户给的是**业务对象名称/中文单据名**，必须先按名称解析并查询对应元数据，禁止跳过这一步直接写代码。
- 如果用户给的是 **URI**，必须按 URI 查询对应元数据，禁止凭名称猜 URI。
- 如果需求已明确给出 YonSQL 的 `uri`、`domain`、字段、查询条件且可追溯，可直接生成，不必强制调用 metadata skill。
- 如果生成代码中出现新的业务对象 URI，但前置步骤里没有对应元数据查询记录，视为门禁未通过。
- 如果需求涉及参照字段，且未查询该参照 `refUri` 对应元数据，视为门禁未通过。
- 如果需求涉及字段取值，但未确认字段类型（基本类型/参照/特征/子表/平行表/多选引用/业务外键关联），视为门禁未通过。
- 如果需求涉及业务外键关联，但未比较源实体和目标实体 `_entityInfo.domain`，视为门禁未通过。
- 如果最终生成代码里出现 URI/domain/字段，但无法回溯到元数据查询结果，视为门禁未通过。

### 3.2 消费清单模板（生成代码时必须输出）

```markdown
## 元数据消费清单

| 字段名/URI | 来源元数据路径 | domain | 必填 | 用途 |
|---|---|---|---|---|
| `org.code` | `bd.adminOrg.BaseOrgVO.attributes[code]` | ucf-org-center | ✅ | 校验管理组织 |
| `crowd` | `aa.vendor.Vendor.attributes[crowd]` | yssupplier | ❌ | 关联组织群 |
| `creditServiceDay` | `aa.vendor.VendorExtend.attributes[creditServiceDay]` | yssupplier | ❌ | 账期字段 |
| `vendorCharacter.XJBL` | `Vendor.characterGroups.vendorCharacter.featureFields[XJBL]` | yssupplier | ❌ | XJBL 现金比例 |
```

**强约束**：消费清单中每一行必须有具体的元数据路径，禁止"凭印象"。

## 四、典型反模式 vs 正确做法

### 4.1 反模式 1：URI 前缀推导 domain

```javascript
// ❌ 反模式
// 看到 bd.xxx 就想当然用 basedoc
var orgIdList = ObjectStore.queryByYonQL(orgIdSql, 'basedoc');

// ✅ 正确
// 调 iuap-c-metadata-info 查 _entityInfo.domain
var orgIdList = ObjectStore.queryByYonQL(orgIdSql, 'ucf-org-center');
```

### 4.2 反模式 2：跨实体套用 domain

```javascript
// ❌ 反模式
// Vendor 的 domain 是 yssupplier，就以为 VendorExtend 也是 yssupplier
var extendList = ObjectStore.queryByYonQL(extendSql, 'yssupplier');
// 实际：VendorExtend 的 domain 可能是不同的

// ✅ 正确
// 即使是同一业务域下的实体，也要逐个查 domain
var extendList = ObjectStore.queryByYonQL(extendSql, '<每个实体独立查到的 domain>');
```

### 4.3 反模式 3：写完 SQL 不跑

```javascript
// ❌ 反模式
// 直接把 SQL 写到代码里，部署后才发现 domain 错
var sql = "select * from `bd.adminOrg.BaseOrgVO` where code = '666666' and dr = 0";
var list = ObjectStore.queryByYonQL(sql, 'basedoc');  // 失败

// ✅ 正确
// 先在开发环境跑一遍验证
var sql = "select id from `bd.adminOrg.BaseOrgVO` where code = '666666' and dr = 0";
var list = ObjectStore.queryByYonQL(sql, 'ucf-org-center');
console.error('验证结果:', JSON.stringify(list));
if (!list || list.length === 0) {
    throw new Error('SQL 验证失败：domain 错或 666666 不存在');
}
```

## 六、检查清单（生成代码前自查）

```
□ 所有 SQL 中引用的 URI 都在元数据消费清单中
□ 每个 URI 对应的 domain 都从 _entityInfo.domain 取（未臆想）
□ 所有字段名都从 attributes[].name 取（未用 dbColumnName）
□ 所有字段都已确认类型：基本类型 / 参照 / 特征 / 子表 / 平行表 / 多选引用 / 业务外键关联
□ 业务外键关联已比较源实体 domain 与目标实体 domain，并据此选择同域 JOIN 或跨域分域查询
□ 所有子表 key 都从 tables.<key> 取（未凭经验）
□ 所有特征组编码都从 characterGroups.<g>.features[].characterCode 取
□ 所有参照 refUri 都二次查过目标实体的 attributes
□ 所有 SQL 都实际跑过验证（非空 + 字段类型符合预期）
□ 代码中有错误处理（空数组 / 非 200 / 异常）
```

**7 项全打勾**才能进入代码生成阶段。
