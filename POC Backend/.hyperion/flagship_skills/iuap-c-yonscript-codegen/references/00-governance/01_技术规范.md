## 规范1：URI特殊字符转义

### 问题背景

部分 URI 包含 `-`（横杠）等特殊字符，直接使用会导致 YonSQL 解析失败：

```
Invalid from clause : cpu-supplymgr.supplystatuschange.SupplyStatusDetail
```

### 正确写法

URI 包含特殊字符时，必须用**反引号**包裹：

```javascript
// ✅ 正确：URI含'-'用反引号包裹
var sql = "select vendorId from `cpu-supplymgr.supplystatuschange.SupplyStatusDetail` where changeId = '" + billId + "'";
var result = ObjectStore.queryByYonQL(sql, 'cpu-supplymgr');

// ✅ 正确：URI含'-'用反引号包裹
var sql = "select id from `cpubase.supplycategory.Supplycategory` where supplyDocId in (...)";
var result = ObjectStore.queryByYonQL(sql, 'cpu-base');

// ❌ 错误：直接使用含'-'的URI会解析失败
var sql = "select vendorId from cpu-supplymgr.supplystatuschange.SupplyStatusDetail..."; // 报错！
```

### 常见含特殊字符的URI模式

| URI模式 | 示例 |
|---------|------|
| `xxx-yyy.zzz.EntityName` | `cpu-supplymgr.supplystatuschange.SupplyStatusDetail` |
| `xxx-yyy.EntityName` | `cpubase.supplycategory.Supplycategory` |

### 判断标准

保守策略：所有跨租户/系统的 URI 统一用反引号包裹，避免出错。

## 规范2：日志打印格式

### 标准格式

```javascript
// ✅ 标准格式
console.error('【MyTrigger】日志内容:' + JSON.stringify(data));
console.error('【MyTrigger】日志内容:' + 变量值);
console.error('【MyTrigger】日志内容:普通文本');

// ✅ 多变量打印
console.error('【MyTrigger】字段1:' + field1 + ', 字段2:' + field2);
```

### 日志标签规范

| 元素 | 规范 | 示例 |
|------|------|------|
| 日志方法 | 必须使用 `console.error` | `console.error(...)` |
| 日志前缀 | `【MyTrigger】` 或 `【MyAPIHandler】` | `【MyTrigger】` |
| 分隔符 | `:` | `【MyTrigger】单据ID:` |
| JSON序列化 | `JSON.stringify()` | `JSON.stringify(data)` |

### 必打日志清单

| 阶段 | 日志内容 |
|------|---------|
| 入参 | `【MyTrigger】入参 param:` + `JSON.stringify(param)` |
| 关键变量 | `【MyTrigger】XXX:` + 变量值 |
| SQL查询 | `【MyTrigger】查询SQL:` + SQL语句 |
| API响应 | `【MyTrigger】API响应结果:` + `JSON.stringify(result)` |

### 禁止写法

```javascript
// ❌ 错误：使用 console.log（生产环境可能不输出）
console.log('【MyTrigger】xxx');

// ❌ 错误：日志格式不统一
console.error('单据ID=' + billId);

// ❌ 错误：未序列化对象直接打印
console.error('【MyTrigger】data:' + data); // data是对象，未JSON.stringify
```

## 规范3：BIP内部API调用

### 调用场景

以下场景必须使用 `ObjectStore.openLinker`：
- 调用**本租户内**的 BIP 标准 API
- 调用**同平台内**的其他微服务接口

**API 门禁**：如果用户没有提供完整 URL、请求方式、入参、出参，必须先调用 `iuap-c-openapi-integration` 查询。禁止按路径规律推导接口地址。

### 标准格式

```javascript
// ✅ BIP内部API：使用 openLinker，自动处理认证
var url = '/yonbip/cpu/cpu-base/bill/batchdeletecategory';
var appCode = 'cpu-base';
var body = { ids: categoryIds };

var resultString = ObjectStore.openLinker('POST', url, appCode, body);
var result = safeJsonParse(resultString, { longFields: [], lengthThreshold: 16 });
```

### URL格式

| 类型 | URL格式 | 示例 |
|------|---------|------|
| BIP内部API | `/yonbip/xxx/xxx` | `/yonbip/cpu/cpu-base/bill/batchdeletecategory` |

## 规范4：跨租户/三方调用

### 调用场景

以下场景必须使用 `ObjectStore.postman`：
- 调用**其他租户**的 BIP API
- 调用**第三方系统**接口（SAP、NCC、浪潮等）
- 需要**手动获取token**并拼接 URL 的场景

### 标准格式

```javascript
// 1. 获取访问令牌
var func = extrequire('GT0000TEN0.token.getToken');
var token = func.execute();

// 2. 拼接完整URL
var env = ObjectStore.env();
var url = env.url + '/iuap-api-gateway/yonbip/xxx/xxx?access_token=' + token.access_token;

var header = { 'Content-Type': 'application/json' };
var body = { data: 'xxx' };

// ✅ 跨租户/三方API：使用 postman
var resultString = ObjectStore.postman('POST', url, header, body);
var result = safeJsonParse(resultString, { longFields: [], lengthThreshold: 16 });
```

### 调用方式对比

| 场景 | 调用方式 | 认证 | URL格式 |
|------|---------|------|---------|
| **BIP内部API** | `ObjectStore.openLinker` | 自动处理 | `/yonbip/xxx/xxx` |
| **跨租户API** | `ObjectStore.postman` | 手动拼接token | `?access_token=xxx` |
| **三方系统** | `ObjectStore.postman` | 根据三方要求 | 完整URL |
| **NCC接口** | `ObjectStore.nccLinker` | nccEnv对象 | 完整URL |
| **其他脚本** | `extrequire('xxx')` | 自动处理 | - |

### 决策流程

```
需要调用接口
    │
    ├──► BIP标准API（本租户内部）
    │    └──► 使用 ObjectStore.openLinker
    │
    ├──► BIP标准API（跨租户）
    │    └──► 使用 ObjectStore.postman + 手动获取token
    │
    ├──► 三方系统API（SAP、NCC等）
    │    └──► 使用 ObjectStore.postman / nccLinker
    │
    └──► 调用其他后端脚本
         └──► 使用 extrequire
```

## 规范5：JSON序列化与解析

### 标准格式

```javascript
// ✅ 序列化：对象转字符串
var jsonString = JSON.stringify(data);

// ✅ 普通 JSON 反序列化：仅限不含业务 Long 主键/外键的普通 JSON
var resultString = ObjectStore.openLinker('POST', url, appCode, body);
var result = safeJsonParse(resultString, { longFields: [], lengthThreshold: 16 });
```

### 常见错误

```javascript
// ❌ 错误：openLinker/postman 返回的是字符串，不是对象
var result = ObjectStore.openLinker('POST', url, appCode, body);
result.code  // undefined！result是字符串

// ✅ 正确：BIP API 返回默认按 Long 风险处理
var resultString = ObjectStore.openLinker('POST', url, appCode, body);
var result = safeJsonParse(resultString, { longFields: [], lengthThreshold: 16 });
result.code  // 正确获取
```

### 决策规则

| JSON 来源 | 推荐解析方式 | 原因 |
|---|---|---|
| `ObjectStore.openLinker` 返回 | `safeJsonParse` | 可能含 19 位业务主键/外键 |
| `ObjectStore.postman` 返回 | `safeJsonParse` | 三方/BIP 返回不可控 |
| `param.requestData` | `safeJsonParse` | MDD 扁平 JSON 未受平台保护 |
| `billDO.customerData` | `safeJsonParse` | 嵌入式业务 JSON 未受平台保护 |
| 手写配置小 JSON 且确认不含 Long | `JSON.parse` | 可用普通解析 |
| `safeJsonParse` 内部最终解析 | `JSON.parse` | 工具函数实现细节 |
```

## 规范6：YonSQL 查询形态与 LEFT JOIN 语法

### 6.1 生产查询底线

- 生产环境禁止 `select *`，必须明确列出返回字段。
- 参照穿透、主子表、多选引用优先使用嵌套子查询，不把 JOIN 作为默认生成策略。
- 不直接生成 `org.name`、`vendor.name` 等穿透字段作为默认 `select` 字段；需要穿透字段时用嵌套查询。
- `where` 右值不要生成实体字段或普通函数；日期、时间、函数结果优先在 JS 侧算好后作为加引号字面量拼入。
- DateTime 比较值必须加引号，例：`pubts > '2025-06-23 19:19:30'`。
- `like`、`leftlike`、`rightlike` 不手写 `%`。
- `group by`、`order by` 只能用当前实体字段，不使用穿透字段、函数或表达式。

### 6.2 LEFT JOIN 语法

### 问题背景

使用 LEFT JOIN 时，左边表（主表）和右边表（从表）的字段引用方式不同：

| 表 | FROM子句 | SELECT/JOIN ON/WHERE |
|---|----------|----------------------|
| 主表（左边） | 不能加别名 | 直接写字段名 |
| 从表（右边） | 必须加别名 | 用别名.字段 |

### ⚠️ LEFT JOIN 跨实体限制（新增）

**YonBIP YonSQL 引擎不支持同一 FROM 子句下 JOIN 多个独立实体。**

当需要关联 `aa.vendor.Vendor` 和 `aa.vendor.CrowdOrg`（两个独立实体，不是子表/孙表），YonSQL 引擎会把 JOIN 别名当作 URI 查找，报错 `entity is null uri:<alias>`。

```sql
-- ❌ 错误：同一 FROM 下 JOIN 两个独立实体
-- 报错：entity is null uri:vdr,name:vdr
SELECT ...
FROM `AT237466701608000A.q97624_vchangereq.q97624_vchangereqChild1`
LEFT JOIN `aa.vendor.Vendor` vdr ON supplier = vdr.id
LEFT JOIN `aa.vendor.CrowdOrg` corg ON vdr.crowd = corg.id
```

**正确做法**：分步查询
1. 先查主表/子表
2. 遍历结果，每条单独查引用实体
3. 校验通过后合并结果

```javascript
// ✅ 正确：分步查询
// Step 1: 只查子表
var subSql = "select supplier from `...Child1` where fkid = '" + billId + "'";
var subRows = ObjectStore.queryByYonQL(subSql, 'developplatform');

// Step 2: 逐行查 Vendor
for (var i = 0; i < subRows.length; i++) {
    var vSql = "select org, crowd from `aa.vendor.Vendor` where id = '" + subRows[i].supplier + "'";
    var vendor = ObjectStore.queryByYonQL(vSql, 'yssupplier');
    // Step 3: 逐行查 CrowdOrg
    var coSql = "select org from `aa.vendor.CrowdOrg` where crowd = '" + vendor.crowd + "'";
    var crowdOrg = ObjectStore.queryByYonQL(coSql, 'yssupplier');
}
```

### 正确示例

```sql
-- ✅ 正确：别名至少 3 个字符
SELECT
    id,
    code,
    crowd,
    corg.org AS useOrgId
FROM aa.vendor.Vendor
LEFT JOIN aa.vendor.CrowdOrg corg ON crowd = corg.crowd
WHERE dr = 0
  AND retailInvestors = 1
  AND corg.org IS NOT NULL
```

### 错误示例

```sql
-- ❌ 错误1：主表加了别名
SELECT Vendor.id FROM aa.vendor.Vendor Vendor
LEFT JOIN aa.vendor.CrowdOrg corg ON Vendor.crowd = corg.crowd

-- ❌ 错误2：SELECT 中主表带别名
SELECT Vendor.id, Vendor.code, corg.org AS useOrgId
FROM aa.vendor.Vendor
LEFT JOIN aa.vendor.CrowdOrg corg ON crowd = corg.crowd

-- ❌ 错误3：JOIN ON 中主表带别名
FROM aa.vendor.Vendor
LEFT JOIN aa.vendor.CrowdOrg corg ON Vendor.crowd = corg.crowd

-- ❌ 错误4：同一 FROM 下 JOIN 两个独立实体
-- YonSQL 引擎把 vdr/corg 当作 URI 查找
FROM `...Child1`
LEFT JOIN `aa.vendor.Vendor` vdr ON supplier = vdr.id
LEFT JOIN `aa.vendor.CrowdOrg` corg ON vdr.crowd = corg.id
-- 报错：entity is null uri:vdr,name:vdr
```

### 多表同名字段处理

当主表和从表有相同字段名（如 `crowd`、`org`）时：

| 场景 | 处理方式 |
|------|---------|
| SELECT 中使用主表字段 | 直接写：`crowd` |
| SELECT 中使用从表字段 | 用别名：`corg.crowd` |
| JOIN ON 中关联 | `crowd = corg.crowd` |
| WHERE 中过滤主表 | `crowd IS NOT NULL` |
| WHERE 中过滤从表 | `corg.org IS NOT NULL` |

## 规范7：字段取值规范

### 核心原则

```
⚠️ 所有字段名必须从元数据的 name 属性获取，禁止使用 dbColumnName
```

### 元数据字段对照

元数据返回格式：
```json
{
  "attributes": [
    {
      "name": "org",           // ✅ 用于 YonSQL
      "dbColumnName": "iOrgId" // ❌ 禁止使用
    },
    {
      "name": "retailInvestors",
      "dbColumnName": "retailInvestors"
    }
  ]
}
```

### 正确 vs 错误

```sql
-- ❌ 错误：使用 dbColumnName（数据库列名）
SELECT iOrgId, bFreezeStatus FROM aa.vendor.Vendor
WHERE iTaxPayingCate = '0'

-- ✅ 正确：使用 name 属性（元数据字段名）
SELECT org, taxPayingCategories FROM aa.vendor.Vendor
WHERE taxPayingCategories = '0'
```

### Boolean 类型值

YonSQL 中 Boolean 字段用 `1`/`0`，不用 `true`/`false`：

```sql
-- ❌ 错误：Boolean 用 true/false
WHERE retailInvestors = true AND stopstatus = false AND bFreezeStatus = true

-- ✅ 正确：Boolean 用 1/0
WHERE retailInvestors = 1 AND stopstatus = 0 AND bFreezeStatus = 0
```

### 禁止臆想字段

所有字段必须来自元数据返回的 `attributes`：

```sql
-- ❌ 错误：臆想字段（未在元数据中确认）
SELECT id, dr, pubts, ext_field FROM aa.vendor.Vendor

-- ✅ 正确：字段都来自元数据 attributes
-- 先查询元数据，确认字段存在后再使用
SELECT id, dr, pubts FROM aa.vendor.Vendor
```

## 规范8：Long 字段精度防御（新增）

### 8.1 为什么要防

YonScript 跑在 V8 引擎上，V8 的 `Number` 是 IEEE 754 双精度浮点，**最大安全整数 = 2⁵³−1 = 9007199254740991**（约 16 位十进制）。但 YonBIP 数据库的 `BIGINT` 是 64 位整数（约 19 位），超过 16 位的整数传给 V8 就会**末位失真**。

**失真示例**：

```javascript
// V8 中
Number(1900000123456789).toString()  // "1900000123456789"（侥幸正确）
Number(1900000123456780).toString()  // "1900000123456780"（侥幸正确）
Number(1900000123456788).toString()  // "1900000123456788"（失真！）
Number(1900000123456790).toString()  // "1900000123456790"（失真！）
```

### 8.2 YonBIP 平台实际保护机制

通过对 `03_YPD扩展点脚本入参结构.JSON` 实际样本分析发现：

| 字段类型 | param.data 中类型 | 失真风险 | 说明 |
|---------|------------------|---------|------|
| 业务主键（id、*_id） | **String** | ✅ 已保护 | 平台已 String 化 |
| 参照外键（orgId、transType、userId、creatorId） | **String** | ✅ 已保护 | 平台已 String 化 |
| 租户数字 ID（param.billDO.tenant） | **Number** | ⚠️ **19 位有失真风险** | 平台保护不完整 |
| 业务状态/枚举（status、verifystate、applyType） | **Number** | ✅ 0~9999 安全 | 值域在 V8 安全范围 |
| 布尔（stopstatus、isDeleted） | **Boolean** | ✅ 安全 | V8 native |

**核心结论**：

- ✅ `param.data[0].id` / `param.billDOs[0].id` —— 平台已 String 化，**直接用 String**，无需处理
- ⚠️ `param.billDO.tenant` —— 19 位 Number，**用 ytenant（String）替代**
- ❌ `ObjectStore.openLinker/postman` 返回的 JSON 字符串 —— **未保护**
- ❌ `param.requestData` 字符串 —— **未保护**
- ❌ `ObjectStore.queryByYonQL` 返回值 —— **未保护**（id 也是 Number）

### 8.3 强约束

**任何 JSON 字符串的反序列化必须用 `safeJsonParse`，禁止直接 `JSON.parse`。**

```javascript
// ❌ 错误：直接 JSON.parse，Long 字段失真
var resultString = ObjectStore.openLinker('POST', url, appCode, body);
var result = JSON.parse(resultString);  // Long 字段已失真
result.id  // 末位可能偏差

// ✅ 正确：safeJsonParse 防御性解析
var result = safeJsonParse(resultString, {
    longFields: ['id', 'purchaseOrderSourceId', 'purchaseOrderSourceDetailId'],
    lengthThreshold: 16
});
result.id  // 始终是 String，不会失真
```

### 8.4 safeJsonParse 工具函数

```javascript
/**
 * YonScript 安全的 JSON.parse，自动处理 Long 字段精度失真
 * 
 * @param {string} content 原始 JSON 字符串
 * @param {object} options 选项
 *   - longFields: 已知 Long 类型字段名（来自元数据）— 第 1 层精确模式
 *   - lengthThreshold: 长度阈值（默认 16，覆盖 V8 安全边界）— 第 2 层兜底
 *   - excludeFields: 已知非 Long 数字字段 — 第 3 层排除
 * @returns {object} 解析后的对象
 * 
 * @example
 * var result = safeJsonParse(content, {
 *     longFields: ['id', 'orgId'],
 *     lengthThreshold: 16
 * });
 */
function safeJsonParse(content, options) {
    if (typeof content !== 'string') {
        return content;
    }
    options = options || {};
    var longFields = options.longFields || [];
    var excludeFields = options.excludeFields || [];
    var threshold = options.lengthThreshold || 16;
    var excludeSet = {};
    for (var i = 0; i < excludeFields.length; i++) {
        excludeSet[excludeFields[i]] = true;
    }

    // 第 1 层：元数据驱动的精确识别
    for (var j = 0; j < longFields.length; j++) {
        var field = longFields[j];
        var escaped = field.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
        var re = new RegExp('"' + escaped + '":(\\d+)(?=[,\\]\\}\\s])', 'g');
        content = content.replace(re, '"' + field + '":"$1"');
    }

    // 第 2 层：长度阈值的通用兜底
    var lengthRe = new RegExp('"([^"]+)":(\\d{' + threshold + ',})(?=[,\\]\\}\\s])', 'g');
    content = content.replace(lengthRe, function (match, key, val) {
        if (excludeSet[key]) {
            return match;
        }
        return '"' + key + '":"' + val + '"';
    });

    return JSON.parse(content);
}
```

### 8.5 四类路径的失真风险矩阵与处理

| 路径 | 拿到的是什么 | 失真风险 | 防御方法 |
|------|------------|---------|---------|
| `param.data[0].id` | 平台已解析的对象 | ✅ 平台保护（String） | 直接用 String，无需处理 |
| `param.billDOs[0].id` | 平台已解析的对象 | ✅ 平台保护（String） | 直接用 String，无需处理 |
| `param.billDO.tenant` | 平台已解析的对象 | ⚠️ 19 位 Number | 优先用 `ytenant`（String），或 `.toString()` 兜底 |
| `param.requestData`（字符串） | 原始 JSON 字符串 | ❌ 必失真 | `safeJsonParse` |
| `ObjectStore.queryByYonQL` 返回 | 平台已解析的对象 | ❌ id 等是 Number | 普通查询 + 结果侧 `String()` / `.toString()` 安全处理 |
| `ObjectStore.openLinker` 返回字符串 | 原始 JSON 字符串 | ❌ 必失真 | `safeJsonParse` |
| `ObjectStore.postman` 返回字符串 | 原始 JSON 字符串 | ❌ 必失真 | `safeJsonParse` |

### 8.6 自动从元数据提取 Long 字段

```javascript
// 从 iuap-c-metadata-info 输出中自动提取 Long 字段
function extractLongFields(metadata) {
    var longFields = [];
    function walk(attrs) {
        if (!attrs) return;
        for (var i = 0; i < attrs.length; i++) {
            var attr = attrs[i];
            if (attr.dataType === 'Long' || 
                attr.dataType === 'Integer' || 
                attr.dataType === 'BigInt') {
                longFields.push(attr.name);
            }
        }
    }
    walk(metadata.attributes);
    if (metadata.tables) {
        for (var key in metadata.tables) {
            if (metadata.tables.hasOwnProperty(key)) {
                walk(metadata.tables[key].attributes);
            }
        }
    }
    return longFields;
}
```

### 8.8 阈值 16 位的合理性

| 数字位数 | V8 安全 | 兜底处理 |
|---------|--------|---------|
| 1~15 位 | ✅ 精确 | 不加引号 |
| 16 位 | ⚠️ 边界 | **加引号（默认阈值）** |
| 17~19 位 | ❌ 必失真 | 加引号（兜底） |
| ≥ 20 位 | ❌ 必失真 | 加引号（兜底） |

**为什么是 16 不是 15**：选 16 是因为业务中**几乎不存在 16 位纯数字的非 ID 数据**（金额、版本号、统计数等远小于 16 位），误伤面为零。如果选 15，反而会误伤一些"看似 ID 实则业务码"的字段。

### 8.9 与其他规范的关系

- **规范 7（字段取值）**：本规范补充了"取值后如何安全使用"——.toString() 是兜底方案
- **规范 8（only-id 反查，SKILL.md 速查表）**：5 步反查法拿到 billId 后，若走 openLinker/postman，**必须**用本规范防御

- ❌ **禁止** 对 openLinker/postman/param.requestData 返回值直接 `JSON.parse`
- ✅ **必须** 用 `safeJsonParse` 替代
- ✅ **必须** `longFields` 参数从 iuap-c-metadata-info 元数据自动提取
- ⚠️ **强烈建议** 在 `safeJsonParse` 之前给关键 Long 字段加日志，便于排查
- ⚠️ **强烈建议** 推动 YonBIP 平台在 `param.billDO.tenant` 字段做 String 化保护

## 规范9：YonSQL 注入防护

> 核心：任何来自用户、前端、三方接口、可编辑字段的值，拼入 YonSQL 前都必须转义；字段名、排序字段、URI、domain 必须白名单。

### 标准工具函数

```javascript
function escapeYonQLString(value) {
    if (value === null || value === undefined) {
        return '';
    }
    return String(value).replace(/'/g, "''");
}

function quoteYonQL(value) {
    return "'" + escapeYonQLString(value) + "'";
}

function buildInValues(values) {
    var list = [];
    for (var i = 0; i < values.length; i++) {
        list.push(quoteYonQL(values[i]));
    }
    return list.join(',');
}
```

### 正确写法

```javascript
var code = quoteYonQL(request.code);
var sql = "select id, code from `aa.vendor.Vendor` where code = " + code;
```

### 禁止写法

```javascript
// ❌ request.code 未转义，存在注入风险
var sql = "select id from `aa.vendor.Vendor` where code = '" + request.code + "'";
```

字段名、排序字段、URI、domain 不能从用户输入直接拼接；必须来自元数据或固定白名单。

### YonSQL 兼容性约束

- 当前 skill 生成 YonSQL 时，**禁止默认使用 `cast(...)`** 作为通用方案。
- 如果没有用户明确说明或平台已验证支持，不要生成 `cast(id as char)` 一类写法。
- Long 字段场景优先通过普通查询 + 结果侧安全处理解决，而不是依赖 YonSQL 函数能力。
- DateTime 比较不要生成 `validtime > now()`，平台会把 `now()` 当字符串导致 DateTime 转换失败；应在 JS 中生成 `yyyy-MM-dd HH:mm:ss` 后用 `quoteYonQL` 拼入。
- 生产环境需要可诊断日志，保留关键 `console.error`，但避免默认 `JSON.stringify(result)` 打印大结果集；推荐打印入参 ID、SQL、行数、返回 ID 数量。

## 规范10：元数据门禁

> **核心**：代码生成前，先判断 YonSQL 四要素是否充分；信息不足时必须查元数据，且 `domain` 必须从 `_entityInfo.domain` 取，禁止臆想。

### 10.1 错误样本（真实生产事故）

```javascript
// ❌ 反面教材
// 凭"URI 前缀是 bd"就推导 domain 为 "basedoc"
var orgIdSql = "select id from `bd.adminOrg.BaseOrgVO` where code = '666666' and dr = 0";
var orgIdList = ObjectStore.queryByYonQL(orgIdSql, 'basedoc');  // 失败
```

**正确做法**：

```javascript
// ✅ 先调 iuap-c-metadata-info 查实体的 _entityInfo.domain
// 实际结果：domain = "ucf-org-center"
var orgIdList = ObjectStore.queryByYonQL(orgIdSql, 'ucf-org-center');
```

### 10.2 7 项门禁清单

```
门禁 1: URI 必查 domain        - 每个新 URI 必查 _entityInfo.domain
门禁 2: 字段名必查 attributes  - 用 name 属性，不用 dbColumnName
门禁 3: 子表 key 必查 tables   - tables.<key>，禁止臆想
门禁 4: 特征组编码必查         - characterGroups.<g>.features[].characterCode
门禁 5: 参照档案必查 refUri    - 二次查 refUri.attributes
门禁 6: SQL 必执行验证         - 写完 SQL 必须跑一次（非空 + 字段类型）
门禁 7: 错误处理必捕获         - 静默失败是最危险的
```

### 10.3 强约束

- ❌ **禁止** 凭 URI 前缀推导 domain（`bd` 不等于 `basedoc`）
- ❌ **禁止** 跨实体套用 domain（即使在同一业务域下，每个 URI 独立查）
- ❌ **禁止** 用 dbColumnName 拼 SQL
- ❌ **禁止** 凭经验写子表 key
- ❌ **禁止** 写完 SQL 不跑就提交
- ✅ **必须** 输出"元数据消费清单"（每条 SQL 对应一行元数据来源）

### 10.4 与其他规范的关系

| 规范 | 关系 |
|---|---|
| 规范 6（查询形态与 LEFT JOIN） | 配合门禁 1（domain 必查），生产禁 `select *`，优先嵌套查询 |
| 规范 7（字段取值） | 配合门禁 2（用 name 属性）|
| 规范 8（Long 防御） | 与门禁正交，独立规范 |
